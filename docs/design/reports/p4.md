## Format and behaviour changes (flagged)

- New block kinds:
  - Project: `{name, description, created_at}` plus `asserted_by`.
  - InputSet: a run's inputs, `{role, name, address, size, sample, reason}` each.
  - Handoff: `{template, selection, project, files, params, timestamp}`.
  DESIGN.md §6 and §22 have them.
- New Store Log kinds: `project` and `handoff`.
- Every RunCompletion this build writes links an InputSet. `input_set: null` now means a run from before P4, and those read as before everywhere.
  - Input roles: `samplesheet` > `param:<name>` > `asset` (files under the pipeline's projectDir) > `task`.
  - `params.input` stays `[redacted-location]` in the RunManifest.
  - Remote inputs (s3, gs, az, http(s), `/fusion/`) are never opened.
  - Names drop any query, fragment and userinfo, so no presigned URL, SAS token or password reaches a block.
  - One `cas.inputs.waitSeconds` deadline bounds stats and hashing; inputs still pending get reason `unfinished`.
  - Measured on an M3 Pro, warm cache: 1.8 GiB/s on one thread, 5.6 GiB/s on four. A run with 4 GiB of inputs waited 0.38 to 0.43 s at completion.
- Older builds:
  - A sweep by a build older than P4 would trash Project and Handoff blocks, a Handoff's files, and anything only its Selection reached, as a pre-P3 build does with Transfer. It keeps InputSets.
  - From this build on, a sweep refuses `--apply` beside any Store Log entry it can't read (the orchestrator's addition), so later kinds are safe against it.
- Index: schema v5 (last round, at the user's direction to prefer clean code over compatibility with older dev builds).
  - Every table is in one DDL, including P3's `transfer`/`transfer_root` and P4's `project`, `project_stats`, `run_input` and `handoff`, with the index `claim_current_attribute_value`.
  - The snapshot is `index/v5.sqlite`. A v4 or v3 cache or snapshot is ignored and rebuilt from the Store Log.
  - The page treats a store with only an older snapshot as having none, and says to run `nf-blocks:snapshot`.
  - A full rebuild of roblab: a cold catch-up in 279 ms, including open, and a snapshot write in 232 ms (1,806,336 B).
- Claims:
  - P4 adds `add` for project, sample, annotation, same_sample and policy.people, and `set` for policy.default_store and policy.retention.
  - P4 attributes supersede only within their own attribute.
  - The Claim block itself is unchanged.
- Behaviour change in P2's code: Put now accepts `add pin` and `del pin` on a Selection. It used to refuse them with `wrong_kind`.
  - The retention milestone plan records the user's answer (ticket 21 answer 6) as "pins on any subject", so this follows that answer.
  - The orchestrator's ruling A.
  - Mark and the P2 figures already treated pins on any subject alike, so only `Put.PINNABLE` changed.
  - P2's own Pin… on the Selection page had been refused by the real server the whole time. Its tests used a recording writer.
  - `ExploreWriteTest` now sends the page's exact pin and unpin requests to the real server.
- Copy (P3's area, expect small conflicts):
  - `CopyClosure.categoryOf` files project and policy.* Claims under `projects`, and sample, annotation and same_sample under `annotations`.
  - Carrying `projects` brings the Project block itself.
  - `CopyService` logs it as `project`.
  - `web/src/views/copy.js`: `copyToButton` takes an optional `to`, and one note line appears when a project's default store isn't a copy target here.
- Endpoints: `POST /api/handoff` is new, and `POST /api/put` builds a third kind, Project.

## differentialabundance and the matrix

Read at tags 2.0.0 (the latest) and 1.5.0. Nothing was run.

- VALIDATOR runs shinyngs `validate_inputs()` then `read_matrix()` (pinin4fjords/shinyngs v2.4.0, `R/accessory.R` L1369-L1376).
  - It stops only when a samplesheet sample has no matrix column (L778-L791).
  - It then returns `as.matrix(matrix_data[, rownames(sample_metadata)])` (L804), which keeps the samplesheet's samples in its order and drops the others.
  - v1.8.8 (pipeline 1.5.0) does the same at L766 and L792.
  - Downstream steps take the validated assay: `workflows/differentialabundance.nf` L405-L414 at 2.0.0, L310-L311 at 1.5.0.
- The DESeq2 template subsets again:
  - `count.table <- count.table[, rownames(sample.sheet)]`;
  - `modules/nf-core/deseq2/differential/templates/deseq2_differential.R` L268-L281 at 2.0.0, `deseq_de.R` L224-L237 at 1.5.0.
- So the template passes the whole merged matrix with a samplesheet of only the chosen samples, and adds no subset step. The page says so in one muted line.
- `--gtf` is optional (default null, `nextflow.config` L47).
  - Without it the matrix doubles as the feature table, and the annotated results may carry count columns for excluded samples (`workflows/differentialabundance.nf` L518-L528). That last point was read from the code, not observed.
  - The GTF check therefore warns, and doesn't block.
- The pipeline checks design rank and levels, not a minimum number of replicates. The ≥ 2 rule is the spec's, and DESeq2 needs residual degrees of freedom, so it blocks.
- Contrasts go as `contrasts.csv`: shinyngs 2.4.0's `read_contrasts` takes `.csv` or YAML only (L985-L1076).
- The defaults `observations_id_col=sample`, `features_id_col=gene_id` and `features_name_col=gene_name` (`nextflow.config` L36, L42, L43) match the salmon matrix.

## Deliberate differences from the mockups

Mockup 13:
- The head has Edit… (rename and policies) and, on the Samples tab, Hand off…. The mockup has no controls for either, but the brief asks for them.
- Ages are relative ("21m"), as every claim tag on the site is. The mockup shows "Oct 23", which is what `age()` writes past a week.
- Activity lists each membership as its own row ("added sharp_magritte"). The mockup groups them ("added 3 runs").
- The copy row reads "copied wigshop from roblab to org-s3", without the arrow (writing rules).

- Item members appear in an Items panel under Runs; there is no Items tab.
- The nav's "Not in a project" has no count, since counting would read every run at load.

Mockup 14:
- The rail's Saves list has more facts than the mockup: the Selection's name ("uninduced vs wild_type (differentialabundance)"), "added to <project>", and the hand-off block. Save writes them, so the list names them.
- The command adds `--outdir results` (nf-core requires it), omits `--gtf` when none is given (the pipeline doesn't need it), and uses full cids. A muted line says cas:// addresses resolve when the run loads nf-blocks with a store that holds them.

- The pin's bytes before Save are labelled "about". They come from the items' file sizes, because the Selection doesn't exist yet.

## Rulings

Phase and interface rulings (the plan's section 2):
- D1: project-scoped Claims hang off the Project, because a sample has no cid. If wrong, annotations move to another subject.
- D2: sample grouping runs in the page, so merges and splits show at once. If wrong, a snapshot grouping table with a tail override.
- D3: a hand-off with no active project writes no condition Claims, and the samplesheet holds them. If wrong, one more Claim subject.
- D4: a Handoff block roots the generated files. If wrong, they need another root.
- D5: retention pins are real pin Claims the page writes. If wrong, Selections added outside the page aren't pinned until someone uses the Pin offer.
- D6: whole matrix plus subset samplesheet (the section above).
- D7: Handoff params are scrubbed in the block, and the response's unscrubbed params build the command. If wrong, a re-opened hand-off can't show a local GTF path.
- D8: no index version bump, with P4 tables added if missing and a one-time rescan. Replaced in the last round by schema v5 (user's direction).
- Q1 (orchestrator): a default store never overrides readOnly.
- Q2 (orchestrator): "same sample as" is project-scoped. A global identity waits on input CIDs and would need a sample subject.
- Ruling A (orchestrator): Put accepts pins on Selections.
- Never download a remote input to hash it; scrub credentials from input names; one wait deadline (orchestrator, F4).
- Sweep refuses `--apply` beside an unknown log kind (orchestrator).

Rulings made during the explorer tasks, each with its cost if wrong:
- Later tasks could add a model or writer method in its own commit. If wrong: a little overlap.
- The Task 5 hand-off entry may edit Task 3's project-samples.js by one link. If wrong: a cross-file edit.
- The GTF check warns. If wrong: one copy change.
- The Projects list has no samples column. If wrong: one column of information.
- "Not in a project" has no count in the nav. If wrong: a mockup difference.
- The Task 3 mockup differences listed above. If wrong: mockup drift.
- Runs reached only through member items are read whole when an added sample names their pipeline, within a 6,000-item project budget. If wrong: extra item reads.
- On a pre-P4 S3 snapshot the page walks the whole Store Log once per open, until the snapshot is rewritten with the P4 tables. If wrong: ceil(N/1000) LIST requests per open.
- Project tags read the Claims each page already loads. If wrong: nothing; the reviewer checked it.
- A sample row's tag shows only explicit `add sample` Claims, since the run's own tag covers run membership. If wrong: a redundant Add offer.
- The hand-off command adds `--outdir results` and a note about loading nf-blocks. If wrong: a small mockup difference.
- With a project active, a hand-off Save also adds the Selection to the project. If wrong: one extra write.

## Open questions

- Activity across stores reads one store and links to the others. Merging events from several members' logs is a follow-up.
- A partial InputSet (some input `unfinished`) isn't visible on the page: `run_input` has no `reason` column. Adding one is an index change.
- The shared-input suggestion query reads every task-input index entry once, which grows with total inputs. It's fine at this size; scope it to recent runs if it gets slow.
- The shared-reference filter catches a file staged for several samples in one run. A reference staged once per run in single-sample runs could still join samples by input. The plugin's rule (a sample only from a `meta` component) makes that unlikely, but it is a plan-level gap.

- Residual minors from the final re-review, left for a follow-up:
  - With both the Edit panel's Pin and the Selections tab's Pin open, `#project-pin-go` appears twice.

- Seen in the final shots, not fixed:
  - The copy page's "Claims to carry" shows a carried project as its short cid, not its name.
  - The long "named" tag there runs a few pixels past the panel edge.
- The scrub still misses four shapes, kept as pending tests: `mysql -p x`, `-px`, a bare base64 `user:pass`, and an AWS session token. It also over-redacts by design: the `name: value` form also reads error prose, so `Missing key: sample` loses `sample`, and `--pass 2` loses `2`.
