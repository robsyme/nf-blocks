## Index schema v4 (this phase owns the bump)

The existing tables are unchanged. New tables in `Index.ddl()`:

| Table | Filled at | Purpose |
|---|---|---|
| `block(cid PK, size, codec)` | ingest | raw file blocks and DirectoryManifests |
| `block_ref(owner_cid, cid, name)` + index `block_ref_owner` | ingest | item → Leaf and manifest → entry edges |
| `root(id PK, cid, kind, asserted_by, state, since)` + indexes `root_cid`, `root_kind` | snapshot | one row per run, Selection, and (pinned subject, asserter) |
| `root_stats(root_id PK, reachable_bytes, reachable_blocks, exclusive_bytes, exclusive_blocks, pinned_bytes, partial)` | snapshot | per-root figures; `exclusive` is "freed on release" |
| `root_shared(root_id, other_root_id, bytes)` + index | snapshot | the top 5 sharers per root |
| `store_stats` (one row) | snapshot | stored, referenced, pinned, held, releasing and shared bytes; partial |
| `asserter_stats(asserted_by PK, reachable, exclusive, pinned, releasing)` | snapshot | per person; the key follows `identity.js` `principalKey`: ASCII whitespace trimmed and ASCII letters lowercased, whatever the JVM locale |
| `pipeline_stats`, `collection_size`, `item_size`, `kind_stats` | snapshot | the index-backed sizes |
| `pinned_overlap(subject_cid, asserted_by, bytes)` + index | snapshot | "already pinned here by", for runs, Selections, collections, items and pinned files |

The snapshot also gets the meta key `sweep_grace_ms`. The cache fills only `block` and `block_ref`; seeding copies both back, plus the content `missing` rows, taking only owners the cache lacks.

Format changes: no block or log format changed. The snapshot moves from `index/v3.sqlite` to `index/v4.sqlite`. The Gate reads and generates v4.

Upgrade note: a v3 cache is recreated, and a store with only `v3.sqlite` can't seed a v4 cache. So the first catch-up after upgrading is a full scan, with the usual "no usable snapshot" warning.

Snapshot size: roblab grows from 954,368 B (v3) to 1,744,896 B (v4). The Gate's synthetic year snapshot grows from 604,672,000 B to 815,443,968 B (+35%). Almost all the growth is `block_ref`, its index and `block`, which seeding needs.

## Rulings (R1 to R9 from the plan, plus those made during execution)

Each says what it costs if wrong.

- **R1 Stored.** Stored counts raw blocks reachable from the member's records, so coordinate-only files and records are left out. If wrong, Stored understates disk use by unreferenced blocks (7.9 MB on roblab) until the next sweep.
- **R2 Referenced.** Referenced counts every (output collection, item) membership; Selections add nothing. If wrong, Referenced (and with it the dedup ratio) is slightly low wherever Selections exist.
- **R3 Roots.** Roots follow `Mark` via `ClaimState`: held, released, deleted, and pinned per (subject, asserter). Pinned + Held + Releasing = Stored. If wrong, the partition drifts from what a sweep would actually keep.
- **R4 Frees** is a root's exclusive bytes against every other content root. If wrong, Frees misreports what a release reclaims.
- **R5** is the pipeline Stored rule above. If wrong, home disagrees with P0's numbers for pipelines with deleted runs.
- **R6** is how a released run reads. If wrong, it is copy only.
- **R7 Grace.** The grace comes from `cas.sweep.grace`. The earliest date is the release time plus the grace, and no sweep date is promised, because sweeps are run by hand. If wrong, the date shown is a lower bound rather than a promise.
- **R8 Cross-store.** Stored counts the blocks reachable from every root of this member, of every kind. So a Selection here counts its items' blocks here, even when another member holds them. If wrong, Stored overstates for cross-member Selections until P3's presence work.
- **R9 Single store.** No card row; the summary heads the breakdown. If wrong, the layout differs from the mockup's multi-store row (P3).
- Ingest's `block` insert fills a NULL size when a later Leaf gives one. If wrong, the only difference from the brief is that a NULL can become a size.
- `pinned_overlap` covers runs, Selections, items, output collections and pinned files. If wrong, it carries a few extra sparse rows.
- A blank `asserted_by` keys as `anonymous`, like null. If wrong, blank and anonymous principals merge in By person.
- The snapshot keeps `block` and `block_ref`, because seeding needs them; the unused `block_ref_cid` index was dropped. If wrong, large members hit the 64 MiB cap sooner than under v3 (see Open questions).
- On v4, `collectionSize` reads its bytes from the index and leaves kind chips to P0's lazy walk. If wrong, the chips still cost the walk.
- The items grids keep `itemSize`'s walk, while the item page reads `item_size`. If wrong, grid size cells stay walk-based.
- `root_kind` index and `pinRoots` query added. If wrong, one small extra index.
- Read-only stores keep the Freed-on-release columns. If wrong, read-only viewers see a figure they can't act on.
- Read-only pages hide the run header's Pin…/Release… buttons, because the spec says read-only stores show no Release/Pin actions. If wrong, read-only viewers lose a jump link.
- The file page has no "already pinned here" line, to stay inside its Gate budget of 8 requests / 64 KB. If wrong, file pins lack the others figure.
- With two or more other pinners, each person's exact figure is listed instead of a sum, because summing overlapping pins overcounts. If wrong, the line is longer.
- Stale figures. When the page holds a pin, retain or deletion Claim written after the snapshot, the Release, Unpin and "already pinned" figures are withheld, and the copy reads "Freed bytes are known once the next snapshot is written". Exclusivity depends on every root, so one such Claim makes every figure on the page suspect. If wrong, figures hide more often than strictly needed.
- With newer runs added, a pipeline's Stored reads "up to <bytes>", because the indexed figure plus walked tail runs can count shared files twice. If wrong, it is only a label.
- The right rail is hidden on `#/storage`. Mockup 09 has none, and the rail clipped By run's Release buttons at 1440. If wrong, the Picked panel is unavailable on that page.
- P0's deferred home subline ("142 MB stored · 220 MB referenced · 1.55× dedup") was added here. If wrong, it is one line.

Parked findings, each judged against the invariant that the figure shown before a click never understates what the action frees:
- In the stale state, the Compare table and the run's storage bar keep snapshot values. They are labelled "as of the snapshot", and the confirmation itself withholds figures.
- On the Storage view, a run released since the snapshot still offers "Release…". The link opens the guarded confirmation.
- New tail runs or Selections can make "Frees X" overstate. Releasing never frees more than shown, and the next snapshot corrects it.
- A pin on a non-output (input) collection reaches nothing in the snapshot, though `Mark` walks it. This is rare.
- A tail run's unreadable blocks don't mark "up to" figures partial.
- The stale note says "pins and releases" even after a deletion.

## Fix round 2 (integrator block on 429b7e9)

The integrator blocked the branch on two plugin bugs and listed should-fixes. Every item below is fixed, reviewed and re-reviewed, unless it is listed as remaining.

### B1: swept content stays in Stored and Releasing

**Approach: a presence check when the snapshot is built.**
- Only blocks reached solely through non-content roots (released or deleted runs, deleted Selections) are checked, with the writable member's `has`. A sweep never removes a block that a held or pinned root reaches, so those are never checked.
- The checks run 16 at a time. A check that throws counts as present.
- A block found absent is remembered per member in a new cache-only table, `block_absent(member, cid)`. `Index.open` creates it with `CREATE TABLE IF NOT EXISTS` after the version check, so an existing v4 cache upgrades in place. If the table can't be made, the memo is off for that session, with one warning, and the cache is never wiped.
- Rows that are no longer candidates are dropped at each build, so a block that comes back gets one fresh check.
- `SCHEMA_VERSION` and the snapshot DDL are unchanged.

I chose this over reading the trash ledgers because a deleted block falls out of every ledger, so the ledgers can't say what is gone.

**Effect on the figures.** An absent block leaves every storage figure: store_stats, root_stats, root_shared, asserter_stats, pipeline_stats, kind_stats and pinned_overlap. `item_size` and `collection_size` stay the record's sizes.

The integrator's repro now gives `[stored_bytes: 1, releasing_bytes: 0]`, and it is kept as a regression test (`IndexSnapshotSweptTest`). On the page, a released run's figures read as what is still stored here. A swept run reads "A sweep may already have reclaimed any files only this run held; its records and lineage stay here", and it never shows a past date.

**Cost.** One HEAD per present block that only released or deleted roots reach, at every snapshot write, until a sweep takes it. When nothing is released there are 0 lookups (asserted on roblab).

An open question for the integrator: a grace-age skip would cut this further. I didn't adopt it, because a sweep can run under a shorter `cas.sweep.grace` than the writer's (the Gate's `grace0.config` does), so a young release isn't safe to skip.

### B2: an OOM in the snapshot write, and the size cap

- `CasObserver` catches `Throwable` around the snapshot write and around the Store Log append. A recorded run now says it was recorded, and names what failed.
- **The lean v4 snapshot.** Before building, the writer estimates the full size as L + refs × m:
  - L is the lean part, measured in the same build before the content is copied.
  - m is the marginal cost per `block_ref` row. It starts at 400 B, from measurements of 389 B on roblab and about 385 B on the year, and is learned per member from full builds.
  - When the estimate is over `cas.snapshot.maxBytes`, or `writeStorage` runs out of memory, the snapshot is written lean, with no content or storage tables. Its meta `storage_omitted` is `over_cap`, `out_of_memory` or `seeded_lean`, plus `snapshot_max_bytes` (only when a cap is in force) and `sweep_grace_ms`.
  - The page says why the figures are missing, and sizes fall back to walking blocks.
  - A member wrongly sent lean corrects itself on the next write, because L is measured.
  - An over-cap verdict for the lean snapshot itself is persisted, so later runs don't rebuild and discard it.
- **`seeded_lean`.** A cache seeded from a lean snapshot has no content edges for those runs, so its snapshots stay lean. The page, the run log and the CLI all name `nextflow plugin nf-blocks:reindex --seed false`. `seedFrom` still accepts lean snapshots, because refusing them would force a full block scan on every ephemeral job.
- **Year check** (gen_year, 547,500 refs), measured by F2:
  - at `-Xmx512m`, a lean `out_of_memory` snapshot of 593 MB, where before the OOM escaped;
  - at a 64 MiB cap, OVER_CAP, and the next write skips the build;
  - at 1536m, a full 804 MB snapshot.
- **Tests.**
  - `SnapshotHeapBoundTest` runs under `memoryBoundTest`'s 48 MiB heap and makes a real `OutOfMemoryError`.
  - `CasObserverTest` covers an OOM in the snapshot write and in the Store Log append.
- **Limitations.**
  - The OOM verdict is sticky at the same `-Xmx` until there is more heap, a forget or a reset.
  - Other threads share the heap during the OOM window.

### Should-fix and minor items

- Hidden on read-only stores, by the orchestrator's ruling, which replaces mine: the Freed-on-release columns (By run and By person), the run tab's Compare panel, and its "Only this run".
- **Stale figures on `#/storage`.** After a pin, release, unpin, or a run or Selection logged since the snapshot, `#/storage` says so, withholds Freed and the Release links, and marks the bar "as of the snapshot". A run released in this session shows the same treatment.
- **Unpin** names the store: "Unpin (kept only by this pin in roblab: …)".
- **Missing records.** A missing OutputItem, or a missing OutputCollection, marks its store and roots partial, so "at least" shows.
- **Cache after a forget.**
  - A content `missing` row that nothing reaches is dropped.
  - An over-limit manifest gets a `missing` row, and the figures are partial.
  - A manifest that names no files is read once.
  - Left: `block` and `block_ref` rows stay after a forget. An over-limit manifest costs about 3 HEADs per catch-up per owner.
- **The clock.** The page reads its time from `ex.now()`, so tests are not date-dependent.
- **Also:**

## Follow-up round (after fix round 3 merged)

### A residual race with a sweep in progress

If a `del retain` restore and a cache's snapshot build both land while a sweep is deleting a batch, the build sees the restored blocks present and memoises them in `block_present`, and then the batch deletes them. That sweep marked before the restore was logged. The memo then kept the deleted files counted until some Claim was ingested anywhere.

The integrator's repro, using the real `Sweep`, is a permanent test.

**The fix:** a build records no presences while the writable member's sweep lock says a sweep may be deleting (`SweepLock.mayBeSweeping`): a lock that isn't released, or one released less than 60 s ago, which covers an abandoned sweep's in-flight batch. It is checked at build start (before the roots are read) and again just before recording. A lock that can't be read counts as held. A release rewrites `sweep.lock` and never deletes it, so a lock that merely exists can't be the test. Lookups and figures are unchanged; only the memo write is skipped.

**Why this is airtight:**
- The build has already ingested the restore, so the restore is in the Store Log before the build starts.
- A sweep that takes the lock after the build-start check marks from that log, so it sees the block as live and keeps it.
- Only a sweep whose mark predates the restore can delete the block, and that sweep holds the lock from before its mark until its deletes finish.

The other option, skipping blocks listed in a trash ledger, is not airtight. With `cas.sweep.grace` at 0, one sweep can write a ledger and delete its blocks after the build has read the ledgers.

**Cost:** while a sweep runs, or after a crashed sweep has left an unreleased lock, builds memoise nothing and re-check the next time.

### A known limitation: re-release from another member

This is my reading of the integrator's "cross-member re-release" case.

A store's figures use only the Claims logged in that store, per R3 and the "every number is per store" rule. A sweep run from a composition, though, reads every member's Store Log, as `Mark` does. So a run that is held in member A, but released by a Claim logged in member B, reads as held in A's figures, while a sweep of A run from a session that includes B may reclaim its files.

The `block_present` memo still follows: the cache ingests B's Claim and drops every member's rows. But A's figures say "held" for files a sweep may take. Aligning the two would mean either counting other members' retention Claims in A's figures, or scoping a sweep's retention to the member's own log. That is a decision for P3's multi-store work.

### B1: a warm cache walked through DirectoryManifests a sweep deleted

The integrator's warm repro: release distraught_murdock, sweep (444 blocks, 71.7 MB), Restore it, snapshot. sad_yonath then offered "Release (frees 15.6 MB)", but the next sweep deleted 25.0 MB. A cold reindex said 25.0 MB.

The closure followed edges from DirectoryManifests that were gone, because only raw blocks were presence-checked. Now:
- Presence checks and both memos cover manifests too.
- An absent manifest is a dead end in the closure, and it marks its root, item, collection and the store partial ("at least").
- A permanent test runs release, sweep, restore, release another run, sweep, with a swept directory, and asserts that the frees each Release shows equals what the sweep then deletes.

### B2: the item page's Pin offer used record sizes

For an item of a swept run with 2 of 15 files left, the page offered "Pin 5.27 MB". `item_size` now counts what is stored here (absent blocks excluded, absent manifests a dead end). The item page's Pin uses it, and the header says how much of the item is stored here when that is less than its files' total.

`collection_size` stays a record size, because the run page labels a released run's outputs "references". This refines R6: an item's figure is what is stored here, and an output's is what its records name.

### Notes on this round

- **"At least" after a sweep.** After the first sweep of a released run that has directory outputs, the store reads "at least" until that run is forgotten, because its swept manifests are dead ends that mark it partial. Cold snapshots already did this through `missing` rows (the integrator's own roblab snapshots have `store_stats.partial = 1`), and warm now matches cold. It will show on most stores after their first sweep.
- **Item and collection partial.** These come from the store's flag, since `item_size` and `collection_size` have no partial column and the round adds no DDL.
- **Follow-ups:**
  - An item that names the same file twice can show "stored here of" without any sweep.
  - The two closure walkers in `StorageStats` could share one loop.
  - `RetentionFixture`'s fixed clock can hide a Claim logged after a sweep behind the Forget watermark, so some older sweep tests may pass vacuously.
  - A sweep suspended mid-batch for longer than the lock's stale age, then taken over and released, can resume deleting. That is the sweep's own assumption, and the memo inherits it.
