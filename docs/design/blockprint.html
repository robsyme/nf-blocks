Data has an address, not a location.

Every file and record in a block store is named by a hash of its bytes. Stores are just places that hold some of those names. Move the data and every link still works, because no link ever pointed at a place.

This page tests a visual language for that idea, then applies it to four explorer screens. Sample rows come from distraught_murdock in roblab. Sizes and other stores are example figures.

01 · Concept model

Four layers. Only the top one changes.

Everything a person can change is a claim: dashed, warm, signed. Everything a person can cite is a fact: solid, sealed, the same everywhere. Stores sit underneath both and are never the identity of anything.

Claims

Signed statements about facts. They supersede each other; the current view is what the UI shows. Append-only, so history is the audit trail.

Stores

Places that hold blocks plus a log and a snapshot index. A store is a property of a block, shown as presence, never as its name.

02 · Primitives

Seven marks carry the whole concept

Each one answers a question people ask about stored data: is this the same thing? who said so? where is it? will it be kept? where did it come from?

Seal

A glyph drawn from the CID's bytes. Same bytes, same seal, in every store and every export. Square cells are raw file blocks; round cells are records. Always paired with the short CID in mono.

Address chip

Seal + short CID + optional name and size. The copy action copies the full cas:// reference. Never shows a path.

bafk…gz3oym bafy…qdajhy · all_samples · 94 KB

Fact vs claim

Facts: solid hairline frame, seal, kind label. Claims: notched tag, warm fill, avatar, verb, age. A claim always points at a fact.

One colour per store, shown wherever an address appears. Filled: held here. Ring: referenced but not held, such as pipeline inputs.

03 · Tokens

Seqera ink and green, plus two separate colour sets

The base comes from the Seqera system: dark-brand ink, brand green as the only accent, Inter and JetBrains Mono. Two extra sets do jobs the brand palette doesn't: store colours (categorical, different in lightness so they work for colour-blind readers) and durability colours (semantic). They never share a hue, so “which store” and “is it safe” can't be confused.

04 · Screen · Storage

How much is stored, pinned, and yours

One card per store, and nothing is summed across stores, because pins and cleanup happen per store. “Yours” counts bytes in that store reachable from your runs, pins and Selections. What a release would free is shown only on the Release button, for that store, because shared blocks make it differ from “yours”.

    07 · Screen · Project
    
A project is a living folder made of claims

    
Selections are frozen lists you cite. Projects are where you work: membership, people and sample annotations are claims, so anything can be added or removed with full history. A project lists addresses, so it can span stores. Samples are grouped across runs by meta.id today. Once the plugin records input CIDs, they can be grouped by input reads instead: same bytes in, same sample.

08 · Decisions
Settled in review round 1

  
    
    
  • Seal: keep.The CID glyph is a core primitive and appears beside every address.
    • 
    
  • Fact / claim split: keep for now.Claims are drawn as tags with a punched hole and a full border.
    • 
    
  • Storage is per store.“Only yours” is dropped from bars and project views. Pins and cleanup differ per store, so a cross-store “freed” number would mislead. “Freed on release” appears only on the Release action and in a store's person table, scoped to that store.
    • 
    
  • Config always travels.RunManifest (params, config, script) is always part of a copy, at every depth.
    • 
    
  • Visual identity: Seqera product.
    • 
    
  • Input CIDs are not recorded yet.In roblab, every RunCompletion has input_set: null, the consumer and missing tables are empty, and params.input is [redacted-location]. Cross-run sample identity starts from meta.id until the plugin fills input_set.
