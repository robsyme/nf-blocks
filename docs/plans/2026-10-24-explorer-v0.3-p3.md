## 1. Interface (agreed first; both halves build against it)

### 1.1 CLI

```
nextflow plugin nf-blocks:copy <root> --to <alias> [--from <alias>]
    [--depth results|lineage|all]            default results
    [--claims names,pins,projects,annotations]  default names,projects,annotations (pins off, see 1.4)
    [--dry-run]                               a bare --dry-run arrives as `--dry-run true`
    [--accept-audit true]                     copy even when the audit (1.6) has findings
    [--format text|json]                      default text; json prints the 1.3 body
```

`<root>` is `selection:<cid>`, `run:<cid>` (a RunCompletion, or anything `fromStore(run:)` takes and `RunRef` resolves), or a bare cid whose block kind decides. `--from` defaults to the first member, in `cas.resolve` order, that holds the root. `--to` must be a configured member other than `--from`. Exit 0 on success (or a dry run), 1 on a failure the verb reports (including audit findings without `--accept-audit`), 2 on a usage error.

`--claims` takes `names`, `pins`, `projects`, `annotations` (comma-joined). `none` means no claims. `retain` (release/restore) and deletion claims never travel: they are about the source's retention.

### 1.2 Which members are copy targets

Any configured member (`cas.stores.<alias>`) except the source, opened writable for this command only. A member is not a target when `cas.stores.<alias>.readOnly = true` (new optional config option; flag it in DESIGN.md §2) or, for a local directory, when the directory is not writable by this process. This is decision D1 below.

### 1.4 Closure (the plugin computes it; the explorer only shows it)

Every depth includes, for each run that produced anything in the closure, the **RunCompletion, the RunManifest and the script block** (a decided requirement, never optional).

*Amended (D7):* every depth also copies the **whole metadata of each such run**: every OutputCollection and OutputItem record it links (records only, no files). Content (raw blocks and DirectoryManifests) follows the depth. So a destination holding only the copy is self-consistent: `Mark` can walk the run and a sweep there is not refused for missing metadata, and the uncopied items show as missing here. These records count in the `run_records` group.

- **results**: the root; nested Selections; the root's OutputItems; their files (raw blocks, DirectoryManifests and everything under them); the OutputCollections the items are reached through (records only, so the destination's index can join item -> run; the other items they name stay references); the run records above. For a `run:` root, results is every collection, item and file of that run.
- **lineage** (decided by p3-plugin, written into DESIGN.md): for each run in the results closure whose `nf/<nf_run_hash>/` records the source member holds, start from the tasks that produced the results' published files and walk TaskRun inputs upstream, transitively; an input lid with a published counterpart in the same run (a FileOutput whose `source` is that lid) is upstream, and lineage adds each OutputItem of that run holding such an address, whole with its files, plus its OutputCollection. When the source has no `nf/` records for a run, the fallback is the run-level join-key rule: the run's items that share a `meta.id` with a results item. `nf/` records never travel (they hold host paths and aren't blocks), so lineage depth from an already-copied store always uses the fallback. `runs[].lineage` says which rule applied.
- A non-null `RunCompletion.input_set` is run metadata and travels in `run_records` at every depth; the `inputs` group is for input content once that is recorded (none today).
- **all**: everything the producing runs stored (every collection, item and file), plus inputs when the source holds them (`input_set` is null today, so usually none).
- **claims** (per `--claims`): for each subject in the closure, the current claims of the chosen categories plus every claim they supersede, transitively, copied verbatim. Categories: names = attribute `name`; pins = `pin`; projects = `project`; annotations = any other attribute except `retain`; deletion (attribute null) never travels.

### 1.5 The Transfer block and its log entry (FORMAT ADDITION: flag in the report and to the orchestrator)

New block kind, added to the IPLD schema union in DESIGN.md §6:

```ipldsch
type Transfer struct {
  schema Int                    # 1
  asserted_by String            # the copying principal (P1b resolution, Identity.resolve with COMMAND_WHAT)
  roots [&Any]                  # the roots asked for, sorted by cid string
  from String                   # source member alias
  to String                     # destination member alias
  depth String                  # "results" | "lineage" | "all"
  claims [String]               # the categories carried, sorted
  runs [&RunCompletion]         # every run whose records the copy carried, sorted by cid string (D8)
  blocks Int                    # blocks in the plan
  copied Int                    # blocks written (the rest were already there)
  bytes Int                     # bytes written
  timestamp String              # ISO-8601 UTC, when the copy finished
}
```

New Store Log kind `transfer` (`StoreLogKind.TRANSFER`): `<rts>-transfer-<cid>`. Copied claims keep their original `asserted_by` and `timestamp` (verbatim blocks); only the Transfer block carries the copier.

Order in the destination: every block, then a log entry of the existing kind for each root-like block copied that the destination log lacks (`run-<completion>` per run, `selection-<cid>` per Selection, `claim-<cid>` per carried claim), then the Transfer block, then its `transfer-` entry last. So a crash leaves at most blocks and ordinary entries, never a Transfer without its content. Then the destination's index is caught up and its Index Snapshot written (failure warns; the copy still succeeded).

Index: ingest a `transfer` entry into a new table `transfer(cid PK, from_member, to_member, asserted_by, depth, claims, blocks, copied, bytes, at)` plus `transfer_root(transfer_cid, root_cid, role)` (`role` is `'root'` for the roots asked for and `'run'` for the Transfer's `runs`) with an index on `root_cid`, created with `CREATE TABLE IF NOT EXISTS` in both cache and snapshot, no schema version bump (a v4 page that lacks the tables ignores them; the explorer checks `sqlite_master` first). The web Store Log parser (`web/src/storelog.js`) must accept the `transfer` kind (explorer half).

### 1.6 Audit and the RunManifest regression test

- `RunManifestAudit` (plugin): given a RunManifest block, report any string in `params` (recursively) or `config` text that is an absolute path, a non-`cas://`/`lid://` URI, the OS user name, or credential-like (AWS key id `AKIA…`/`ASIA…`, `-----BEGIN … PRIVATE KEY-----`, `ghp_…`/`github_pat_…`, Seqera/Tower tokens, `key|secret|token|password|credential = <value>` not equal to `'[secret]'`). Every dry run audits every RunManifest in the closure; `plan.audit` lists findings. A real copy with findings exits 1 unless `--accept-audit true`.

Also run the audit over the roblab store's RunManifests (`/tmp/cas-exploration/store`, opt-in system property like `RoblabStorageTest`) and report what it finds.

### 1.7 Explore server (plugin half implements; explorer half consumes)

`members.json` gains, per member:

```jsonc
{ "alias": "org-s3", "writable": false, "base": "m/org-s3/",
  "kind": "local" | "s3",
  "location": "s3://lab-blocks" | null,   // S3 bucket/prefix only; never a local path
  "copy_target": true, "copy_reason": null | "readOnly is set for this store" | "this process can't write the directory" }
```

and top-level `"copy": true` when the server can run copies (it was started with the token).

```
POST /api/copy[?dry_run=true]
  headers: X-NF-Blocks-Token, Content-Type: application/json
  body: { "root": "selection:<cid>" | "run:<cid>", "from": "<alias>" | null, "to": "<alias>",
          "depth": "results" | "lineage" | "all", "claims": ["names", …], "accept_audit": false }
  200: the 1.3 body.  400: bad request (JSON {"error": code, "message"}).  403 token.  409: audit findings without accept_audit, or a root or run released or deleted at the destination (D9): the body is the 1.3 plan with `refused` set; `{"error": "superseded"}` for a dry run that a newer one from the same server replaced while it waited; `{"error": "copy_running"}`. `refused: "not_kept"` wins over `"audit"` when both apply. 503 `{"error": "stopping", "message"}`: a dry run still waiting when the server stops.  500: failure (1.3 body with failures when the copy started).
```

Synchronous: the response arrives when the copy finishes. Same token, origin and size checks as `/api/put`. One copy at a time per server (a second gets 409 `{"error": "copy_running"}`). After a copy the server's own view of the destination (snapshot, log) is what the page re-reads; nothing is cached server side.

### 1.8 Cross-member re-release (handed over from P2): decision D2

Rule (amended, D2): **a sweep of member A releases or deletes a subject only when both A's own Claims and the whole composition's Claims say so, and keeps anything pinned in any member.** A's storage figures use A's own Claims, so a sweep never takes what A's figures call held (the P2 bug). The one mismatch left is the safe one: A's "freed on release" can include a block that a pin in another member still keeps. Roots logged in other members still protect A's blocks during a sweep (unchanged). Narrowed while building: the both-views rule applies to runs and Selections that A's own Store Log lists; ones logged only in other members are judged by the composition's Claims, as before P3 (otherwise A could never release its copies of them). Pins count from any member for every subject. The first draft ("counts only where logged") was not strictly safer than today: it ignored other members' pins and a `del retain` in B superseding a release in A. Copy never carries `retain` or deletion claims, and carries pins only when asked. Document in DESIGN.md §19 and test: a run held in A and released only in B is kept by a sweep of A from a session that includes B, and A's figures agree. If Mark's code makes this rule unsafe or much larger than expected, the plugin lead says so before building it.

## 2. Decisions

- **D1 Copy targets.** Any configured member except the source, unless `readOnly = true` or a local directory isn't writable. Mockup 11 and the shell show several writable stores; one config has one writable member for runs (`lineage.store.location`), so copy opens its destination writable for the command only. The cost if wrong: a config option to remove, and copies into members someone meant as read-only (mitigated by `readOnly`).
- **D2 Re-release.** Section 1.8.
- **D3 Pins.** Off by default (mockup 11 spec): pins state intent in a store, so the destination confirms them. `--claims pins` carries them verbatim.
- **D4 Presence in the page.** For the open member: what the index says (held, or ring when the page knows it is missing here). For other members: a `HEAD <member base>blocks/<xx>/<cid>`, cached per page load, issued only when more than one member is configured. The Gate's single-member budgets are unchanged.
- **D5 "All stores".** A switcher mode (`?member=*`): Pipelines (home), Selections, Search and Storage list every member's rows with presence dots (Storage shows one card per store, never summed). Detail pages open in the first member, in `members.json` order, that holds the root, and say so.
- **D7 Whole run metadata travels.** Section 1.4 amendment (p3-plugin's proposal C). If wrong, a copy carries a few hundred extra small records per run.
- **D8 Transfer names its runs.** `runs` in the Transfer block and `role` in `transfer_root`, so a destination snapshot can presence-check content reachable from transferred runs (P2's R8 overstatement after a partial copy) and the run page can say "Copied here from…" for a run brought in under a Selection. If wrong, one extra field in a new block kind.
- **D9 Kept, not just present (final review).** A copy whose root or any run is released or deleted at the destination is refused (CLI exit 1, endpoint 409 `refused: "not_kept"`), with the destination state in the plan. Copy never writes a restore Claim: the user restores in the destination first. The page never offers "Release here" unless the plan says `kept: true`. If wrong, a copy that should have restored needs one extra step at the destination.
- **D10 Dry runs supersede (final review).** At most one dry run waits per server; a newer one replaces it and the older answers 409 `superseded` (reverses the earlier "dry runs never 409"). The page debounces re-plans and ignores `superseded`. If wrong, a slow server answers fewer stale plans.
- **D6 Synchronous copy endpoint.** No per-group progress stream in v1; the page shows a running state, then the result per group. Deliberate difference from mockup 11's "progress per block group".
