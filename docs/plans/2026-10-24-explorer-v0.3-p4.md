## 1. Interface (agreed first; both halves build against it)

Sample references, used by several claims below:

```
SampleRef = { pipeline: String, id: String }              # meta.id within that pipeline's runs
Occurrence = { pipeline: String, id: String, run: &RunCompletion }   # one run's sample
```

### 1.1 The Project block (FORMAT ADDITION: flag in the report and to the orchestrator)

```ipldsch
type Project struct {
  schema Int                    # 1
  asserted_by String            # created_by
  name String                   # 1..256 characters, the name at creation
  description String            # may be empty, at most 4,096 characters
  created_at String             # ISO-8601 UTC with milliseconds, from the request
}
```

- Written through `POST /api/put` as a third buildable kind: request `{kind: "Project", name, description, created_at}`. The server fills `schema` and `asserted_by`, as for Selection and Claim. Same validation codes (`invalid` for a bad shape, `clock_skew` on `created_at`, as for a Claim's `timestamp`).
- New Store Log kind `project`: `log/<rts>-project-<cid>`. The Project is a root: this build's sweep keeps it until a current `delete` Claim on it (as a Selection). A build older than P4 ignores `project` entries, so its sweep would trash Project blocks, as with Transfer.
- Renaming is a `set name` Claim on the Project, as for Selections. The page shows the current name Claims' values, falling back to the block's `name`.
- `nf-blocks:put` accepts `--kind Project` like the other two.

### 1.2 Claims on and about projects (no Claim format change)

All are ordinary Claims (DESIGN.md §6). `add` groups are sets (ticket 21 answer 2), so current values never conflict by being several; one `(sample, name)` edited twice without superseding shows as a conflict on the page (1.6).

| Claim | subject | verb | attribute | value | Removed by |
|---|---|---|---|---|---|
| Membership | RunCompletion, Selection or OutputItem | `add` | `project` | link to the Project | `del project` superseding it |
| A sample in the project | Project | `add` | `sample` | `SampleRef` | `del sample` superseding it |
| Annotation (project-scoped) | Project | `add` | `annotation` | `{sample: SampleRef, name: String, value: String}` | an `add annotation` superseding it (edit) or `del annotation` (clear) |
| Same sample as (merge / split) | Project | `add` | `same_sample` | `{a: Occurrence, b: Occurrence, same: Bool}` | `del same_sample` superseding it |
| Default store policy | Project | `set` | `policy.default_store` | member alias, String | `del policy.default_store` |
| Retention policy | Project | `set` | `policy.retention` | `"pin_selections"` or `"none"` | `set` again, superseding |
| People (advisory) | Project | `add` | `policy.people` | principal, String | `del policy.people` |
| Rename | Project | `set` | `name` | String | as today |
| Delete / undo | Project | `delete` / `del` | null | null | as today |

`Put` validation (plugin):
- `add project`: the subject is a RunCompletion, Selection or OutputItem the composition holds; the value is a link to a Project the composition holds (`not_found` otherwise, `wrong_kind` for another kind).
- Claims whose subject is a Project accept only the attributes above. `annotation.name` matches `[A-Za-z_][A-Za-z0-9_.]{0,63}`; `annotation.value` is at most 256 characters; SampleRef strings are non-empty and at most 256 characters; `policy.retention` is one of the two values; `policy.default_store` is a non-empty string (not checked against `members.json`: a project travels between explorers with different members).
- `add` may supersede earlier Claims of the same subject and attribute (the edit). `del` supersedes at least one.
- Everything else as DESIGN.md §16 decision 6.

Claim values hold links (`add project`, `Occurrence.run`). The index keeps a non-string value as DAG-JSON text (§16 decision 4), so a membership row's `value` is `{"/":"bafy…"}`. The plugin adds `index claim_current(attribute, value)` so "members of a project" is not a scan.

### 1.3 InputSet: populating `RunCompletion.input_set` (FORMAT CHANGE: flag)

`input_set` links a new InputSet block (the kind name was reserved):

```ipldsch
type InputSet struct {
  schema Int                    # 1
  asserted_by String
  inputs [Input]                # sorted by (role, name, address string); one entry per (role, address, sample)
}
type Input struct {
  role String                   # "samplesheet" for params.input; "param:<name>" for a file another param names; "task" for a file a task staged from outside the run
  name nullable String          # the file's base name only, never a path
  address nullable &Any         # the content's cid, computed even when the store does not keep the bytes; null when not hashed
  size nullable Int
  sample nullable String        # the join key value (meta.id) of the task input tuple that staged it, when it had one
  reason nullable String        # why address is null: "unaddressed" (not hashed by policy), "unreadable", "remote"
}
```

- Files a run reads from outside its own work directory and outside its own published outputs. Content already addressed (a `cas://` input, a `fromStore` item) is recorded with its address and no hashing.
- The plugin decides and measures what hashing costs (design doc §4 experiment 4) and whether that needs a config switch. The report states the measured cost.
- `params.input` stays `[redacted-location]` in the RunManifest. Its address is in the InputSet with role `samplesheet`.
- Old RunCompletions (`input_set` null) stay readable everywhere.
- The InputSet is reachable from its RunCompletion, so the sweep keeps it with the run (an older build's mark already visits `input_set` and keeps an unknown kind, so InputSet is no sweep risk). Mark doesn't follow an InputSet's input addresses: a run doesn't own its inputs.
- An input whose bytes the store doesn't hold is never a `missing` row (that table is re-asked on every catch-up). The page gets presence from `run_input.address` against the snapshot's presence, as for leaves. *(Amended after p4-plugin's review, objection A.)*
- `sample` is set only from the input tuple that holds the file; a separate `path` input gets null. Role precedence is `samplesheet` > `param:<name>` (matched by base name, since tasks see the staged copy) > `task`. Remote inputs that Nextflow staged locally are hashed from that copy; one the head node would have to fetch gets `reason: "remote"`, except `params.input` (read remotely, capped at 16 MiB). *(Objection B and clarification 2.)*

Index (plugin): fill `consumer(content_cid, completion_cid, name, how)` with `how` = role, and add

```
run_input(completion_cid, role, name, address, size, sample)
  index (address)
  index (completion_cid)
```

The page uses `run_input` for:
- a run's inputs;
- grouping occurrences by shared input addresses (1.6);
- suggestions: runs that share at least one input address with `sample` not null.

### 1.4 Project index tables (plugin)

```
project(project_cid PRIMARY KEY, name, description, created_by, created_at)
project_stats(project_cid, reachable_bytes, pinned_bytes, held_bytes, releasing_bytes, roots)
```

- `project` rows come from Project blocks the member's Store Log announces (`project` entries), as Selections come from `selection` entries.
- `project_stats` is per store, computed at snapshot time from the current membership Claims (RunCompletion, Selection, OutputItem subjects). It is the union of their reachable blocks in this store, never a sum of root figures. Same segment rules as P2's `asserter_stats`. `roots` is how many member roots this store holds. On a lean snapshot, no rows (the page says so, as P2 does).
- New tables are created `IF NOT EXISTS` in the cache and the snapshot. The plugin decides whether this needs a schema version bump or a backfill marker (P3's follow-up is doing an index migration for Transfers; match its approach and tell the P4 lead which). The page checks `sqlite_master` and shows nothing on snapshots without the tables.
- The plugin lands the DDL in `web/test/fixtures/schema.sql` first, so the web half builds against it.

### 1.5 Hand-off endpoint and the Handoff block (FORMAT ADDITION: flag)

```ipldsch
type Handoff struct {
  schema Int                    # 1
  asserted_by String
  template String               # "nf-core/differentialabundance"
  selection &Selection
  project nullable &Project
  files [Leaf]                  # the generated files (samplesheet.csv, contrasts.csv), sorted by name; each Leaf {kind: "Leaf", name, address, size, reason: null}
  params {String:String}        # the downstream params, every file one as cas://<cid>/<name>
  timestamp String              # ISO-8601 UTC with milliseconds, from the request
}
```

`POST /api/handoff` (`application/json`, the same token, Host/Origin and size checks as `/api/put`; `?dry_run=true` writes nothing):

```
request:  { "template": "nf-core/differentialabundance",
            "selection": "<cid>",                 # already written through /api/put
            "project": "<cid>" | null,
            "files": [ { "name": "samplesheet.csv", "text": "sample,condition\n..." },
                       { "name": "contrasts.csv",   "text": "id,variable,reference,target\n..." } ],
            "params": { "input": { "file": "samplesheet.csv" },
                        "contrasts": { "file": "contrasts.csv" },
                        "matrix": "cas://bafkreibxyh…/salmon.merged.gene_counts.tsv",
                        "gtf": "/path/or/cas://…" },
            "timestamp": "2026-10-25T…Z" }
response: { "address": "<handoff cid>", "files": [ { "name", "address", "size" } ],
            "params": { "input": "cas://<cid>/samplesheet.csv", ... },   # file references resolved
            "entry": "<log entry name>", "written": true|false }
errors:   plain JSON { "error", "message" }: 400 bad_request | not_found (selection or project) | wrong_kind | too_large; 409 not_writable
```

- File `name`s are base names (`[A-Za-z0-9._-]{1,128}`, unique). `text` is stored as its UTF-8 bytes, unchanged: the page sends LF line endings and a trailing newline. Each file is a raw block. The server checks nothing about CSV content.
- Write order: the raw blocks, the Handoff, then a `handoff` Store Log entry (`log/<rts>-handoff-<cid>`) last. The Handoff is a root and its files are reachable from it. A build older than P4 would trash both (flag).
- The page computes the raw cids itself (sha2-256, raw codec, CIDv1 base32) to show `cas://` addresses live before Save, then uses the server's answer.
- A `params` value is a string, or `{file: <name>}` naming one of `files`.

### 1.6 Sample identity (explorer)

The page groups occurrences into samples with one pure function, `web/src/sampleid.js`, pinned by `web/test/fixtures/sample-vectors.json`.

1. Occurrences: every `(run, meta.id)` of the project's runs (whole-run members), plus those of member items and Selections' items, plus `sample` claims' SampleRefs, matched against those runs.
2. Automatic edges:
   - Two occurrences that share an input address in `run_input` rows with `role = 'task'` and `sample` equal to their `meta.id`. An address that carries more than one distinct `sample` within one run is skipped (a shared reference, e.g. a salmon index staged per sample). Suggestions use the same filtered rows. *(Objection B.)*
   - Two occurrences with the same `pipeline` and `meta.id`, unless both have input rows and share none (same name, different reads: different samples).
3. Remove the automatic edges a current `same_sample` Claim with `same: false` names, between `b` and every occurrence of `a`'s automatic group (split: `b` leaves the group).
4. Add edges for current `same: true` Claims (merge).
5. Connected components are samples. A sample's label is its most common `meta.id`; ties go to the alphabetical first.
6. The basis shown is "input reads" when every occurrence in a component has input rows, otherwise "sample ID".

Annotations attach to a sample through any of its occurrences' SampleRefs. Two current annotation Claims with the same name on one sample, and different values, show as a conflict on the cell.

### 1.7 Policies on the page

- Default store: "Copy to…" from any project member preselects it when it is a copy target. When it names a member this explorer doesn't know or one that is read-only, the copy page says so and preselects nothing (pending the orchestrator's ruling, 2.Q1).
- Retention "pin every Selection": goes through P2's pins.
  - Adding a Selection to such a project, saving a hand-off into one, and turning the policy on each write `add pin` Claims with the note `project policy: <project name>`. Only for Selections not already pinned by the writer, and only in the open writable member.
  - Each shows P2's pin bytes before commit: kept here, and how much is already pinned here by others.
  - Turning the policy off writes no unpin. The page lists the policy pins and offers Unpin per Selection.
- People: advisory, shown as avatars on the project head. Nothing is enforced.

### 1.8 Copy categories (plugin; P3-adjacent, flag)

`CopyClosure.categoryOf`:
- `project` and `policy.*` go to `projects`;
- `annotation`, `same_sample` and `sample` go to `annotations`;
- `name` stays `names`.

When the `projects` category is carried, the closure also carries each Project block named by a carried membership Claim, with that Project's current and superseded Claims in the carried categories. So a destination opened alone can name the project.

## 2. Decisions

- D1 Project-scoped claims hang off the Project. A Claim's subject must be a cid and a sample has none, so sample membership, annotations and merges/splits are Claims on the Project with the sample in the value. Membership of runs, Selections and items is a Claim on the member, as the design doc has it. If wrong: annotations move to another subject, and the page's join changes.
- D2 Sample grouping runs in the page (1.6), not the index. Merge and split must show at once, from the page's own writes, so the page has to group anyway. The plugin supplies `run_input` with the `sample` association, which is what "switch identity to input CIDs" needs from the plugin. If wrong: a snapshot-time grouping table that the page overrides with its tail.
- D3 Without an active project, a hand-off writes no condition Claims. The samplesheet block holds them, and the page offers "Add to project" to keep them as Claims. If wrong: one more Claim subject (the Handoff).
- D4 A Handoff block roots the generated files, so the sweep keeps them and the hand-off is citable. If wrong: the files would need another root.
- D5 Retention pins are real pin Claims written by the page at the three moments in 1.7, never inferred by the sweep. If wrong: Selections added by someone without the page aren't pinned until someone opens the project. The project page shows "N Selections not pinned by policy · Pin".
- D7 Handoff `params` are scrubbed in the block by the same `Leaks` scrub as RunManifest params, so a local GTF path is stored as `[redacted-location]`. The endpoint's response `params` are unscrubbed and never stored; the page builds the command from them. Also an index table `handoff(cid PK, template, selection_cid, project_cid, asserted_by, at)` for the Activity tab. If wrong: a re-opened hand-off can't show the GTF path.
- D8 No schema version bump. P4 tables are created IF NOT EXISTS; a cache that gains them, or is seeded from a snapshot without them, rereads each member's Store Log once for `project`/`handoff` entries and each RunCompletion with an `input_set`. Matches P3's planned F1; both edit `Index.groovy`'s gain-tables/seed code.
- D6 The matrix default (whole matrix plus subset samplesheet, or a subset step) follows the pipeline source check (section 3). Cited in the report.

### Questions sent to the orchestrator (build with the stated default; don't block)

- Q1 A project's default store names a member that is read-only here (or unknown). Default: say so on the copy page, preselect nothing, never override `readOnly`.
- Q2 "Same sample as" is project-scoped (D1). A global version would need a sample subject. Default: project-scoped only.

## 3. differentialabundance: does it subset the matrix?

Checked against the pipeline source at tags 2.0.0 (latest) and 1.5.0. Nothing was run.

- It subsets, twice. VALIDATOR (shinyngs `validate_inputs` → `read_matrix`, pinin4fjords/shinyngs v2.4.0 `R/accessory.R` L778-L791 and L804) stops only when a samplesheet sample has no matrix column, then returns `matrix_data[, rownames(sample_metadata)]`. Downstream steps take the validated assay (`workflows/differentialabundance.nf` L405-L414 at 2.0.0). The DESeq2 template subsets again: `count.table <- count.table[, rownames(sample.sheet)]` (`modules/nf-core/deseq2/differential/templates/deseq2_differential.R` L268-L281 at 2.0.0; `deseq_de.R` L224-L237 at 1.5.0).
- Default: pass the whole matrix with the subset samplesheet. No subset step. The check that matters is the reverse one: every samplesheet sample must be a matrix column.
- `--gtf` is optional (default null). Without it the matrix doubles as the feature table, and the annotated results may carry count columns for excluded samples (read from the code, not observed). So the GTF check is a warning, not a blocker; the copy says what passing one changes.
- Replicates: the pipeline checks design rank and levels, not a minimum per level. The ≥ 2 per side rule is the spec's (and DESeq2 needs residual degrees of freedom), so it stays a blocking check.
- Contrasts go as `contrasts.csv` (shinyngs 2.4.0 `read_contrasts` accepts `.csv` and YAML only). Samplesheet column `sample` (no spaces); defaults `observations_id_col=sample`, `features_id_col=gene_id`, `features_name_col=gene_name` match the salmon matrix.

Full notes and permalinks: the research note in the report.
