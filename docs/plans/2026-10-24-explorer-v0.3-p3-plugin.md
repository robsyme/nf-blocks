## Decisions taken while reading the code

- **Lineage depth (1.4).** Task-level lineage exists. A run's writable member keeps Nextflow's records under `nf/` (roblab: 1,734 FileOutput, 235 TaskRun, 235 TaskOutput, 4 WorkflowRun). A published FileOutput (`nf/<nf_run_hash>/<publish path>`, path `cas://<cid>/<name>`) names its `source`, `lid://<task>/<file>`. That task's TaskRun `input` names the files it read, also as `lid://<task>/<file>`. Those are work-dir files, never `cas://` ones (1,905 of 1,905 resolved inputs). But many have a published counterpart: a FileOutput under the same run whose `source` is that same lid. In roblab, 366 of 784 published sources have a published upstream. Rule:
  - For each run in the results closure whose `nf/<nf_run_hash>/` records the source member holds, start from the tasks that produced the results' published files and walk TaskRun inputs upstream, transitively. Every input with a published counterpart in that run adds that address.
  - Lineage then adds each OutputItem of the run that holds such an address (through the index's `producer` rows), whole, with its files, plus its OutputCollection.
  - Fallback, per run, when the source member holds no `nf/` records for it: anything already copied once, since `nf/` never travels, or a member that cannot be listed. Lineage adds every item of that run that shares a `meta.id` value with an item in the results closure.
  - The plan says which rule each run used (`runs[].lineage`: `"tasks"`, `"join_key"` or `null` below lineage depth; a field added to 1.3's `runs` entries).
- **`nf/` records never travel.** They hold host paths (`workDir` files) and are not blocks; copy reads them only to compute the closure.
- **The Transfer block roots itself** in `Mark`, like a Forget: a sweep keeps it. Its `roots` and `runs` are not followed: the ordinary entries the copy writes root those. A build older than P3 ignores `transfer` entries (`StoreLog.parse` warns once), so its sweep would trash the Transfer block and leave the entry dangling. That is reported as a format note.
- **Copy session.** The copy runs in a composition whose writable member is the destination: `CasConfig.from(config, 'cas://<to>')`. Its other members are the configured `cas.resolve` members plus the source when `resolve` leaves it out. That composition's cache index (its own cache file) is caught up before the plan, so claim and producer lookups work. After the copy, its catch-up and `snapshotWritable` write the destination's snapshot. The source member is read through its own `BlockStore` from that composition, never through the composite, so `missing_at_source` is the source's truth.
- **Verification on write** is the existing `put(cid, in, size)`: `LocalBlockStore` and `S3BlockStore` both hash and refuse a mismatch.

### T1 Transfer kind, index tables, snapshot rows, Mark root
- `StoreLogKind.TRANSFER('transfer')`. `Records.TRANSFER = 'Transfer'`.
- `core/Transfer`: the 1.5 struct with D8 `runs`. Build with `toCbor()`; read with `fromCbor(Map)`, which checks kind and schema 1, sorts `roots`, `runs` and `claims`, and refuses a wrong shape with `IllegalArgumentException`. Field names in snake_case as 1.5.
- Index: `transfer(cid PK, from_member, to_member, asserted_by, depth, claims, blocks, copied, bytes, at)` with `claims` comma-joined and `at` the block's `timestamp`. `transfer_root(transfer_cid, root_cid, role)`, `role` `'root'` or `'run'`, `index transfer_root(root_cid)`. Created `IF NOT EXISTS` on open of an existing v4 cache (like `block_absent`) and in `ddl()`. No `SCHEMA_VERSION` bump.
- Ingest `transfer` entries in catch-up, rebuild, the `missing` retry and `log_entry`, as Claims are. A Transfer block not yet arrived leaves `missing(NULL, cid)` and is retried. `Index.forget` removes rows keyed by a forgotten Transfer cid.
- `IndexSnapshot`: copy `transfer` and `transfer_root` rows of the Transfers whose `log_entry` names the member. Seeding copies them back.
- `Mark`: a `transfer` entry roots its own block only (SELF), like `forget`. Dangling when absent.
- Tests: Transfer round trip and refusals. Ingest from a log, idempotent across overlap. Snapshot carries rows for its member only. A seeded cache has them. A v4 cache opened without the tables gains them. Mark keeps the Transfer block and does not walk its roots.

### T4 Closure
- `CopyClosure.compute(BlockStore source, Index index, String fromAlias, Root root, String depth, Set<String> claimCategories, LineageRecords nf)` -> `CopyClosure.Result`:
  - `blocks`: ordered, distinct `Entry{cid, group, size (Long or null), kind}`, groups in 1.3 order.
  - `runs`: `{completion, manifest, script, runName, pipeline, lineage}`.
  - `claims`: `{cid, category, subject, verb, attribute, value, assertedBy, timestamp}`.
  - `skippedClaims`: `pins`, `retain`, `deletion`.
  - `unaddressed`, `missingAtSource`, `depths` (each depth's blocks and bytes).
- Rules: 1.4 with D7. Runs are found from collections (`run` -> RunManifest -> `Index.runByManifest`) and from Selections' `via`. Whole run metadata (every collection and item record) goes in `run_records`, the selected root's items in `items`, and the via collections in `collections`. A block goes in the first group that claims it. Files are raw leaves, DirectoryManifests and everything under them, read from the source. `unaddressed` counts Leaves with null address. `missing_at_source` counts closure cids the source member lacks.
- Claims: subjects are every closure cid. Only Claims logged in `fromAlias` (`log_entry.member`) count. Current per `ClaimState` over those, by category (names = `name`, pins = `pin`, projects = `project`, annotations = other non-null attributes except `retain`), plus everything they supersede, transitively. Claims not carried are counted in `skippedClaims` by reason.
- Sizes: the `block` table, else Leaf/entry size, else the encoded length for records, else `source.size(cid)`. Unreadable sizes count as `unsized`.
- Index queries needed go in `Index` as public methods with SQL constants.
- One walk serves all three depths: compute the `all` closure once and tag every block and claim with the shallowest depth that includes it (`results` < `lineage` < `all`; all includes lineage includes results). `Result.at(depth)` filters, and `depths` comes from the same walk. Root is already resolved by the caller to `Root{kind: 'selection'|'run', cid}` (a Selection cid, or a RunCompletion cid); parsing `selection:`/`run:`/bare cids is T6's.
- Groups beyond results (1.3 order: root, items, files, collections, run_records, lineage, run_outputs, inputs, claims): `lineage` holds the upstream content only (lineage and all depths), `run_outputs` the rest of what the producing runs stored (all depth only), `files` the root's own files at every depth. Item and collection records are always in `run_records` (D7), so `lineage` and `run_outputs` hold files only. `inputs` is 0 while `RunCompletion.input_set` is null; when it is a link, it is counted there and read like a record.
- Call `TaskLineage.upstream` once per run, with every results address of that run (on S3 it reads every FileOutput record of the run). A run whose RunManifest's `nf_run_hash` is `unknown` or has no records takes the join-key fallback. The join key is the item metadata path `meta.id` (via `item_attr`).
- Reads go to the `source` member's own BlockStore. Lookups (`runByManifest`, producers, `item_attr`, claims, `log_entry`) go to the index of the copy composition, which the caller has caught up.
- Measure on a scratch copy of roblab (copy the store directory first; the test is opt-in like `RoblabAuditTest`). Use the wigshop Selection `bafyreib2rljbxplvhdgbxoqfxujbc2bhztqueg7u35xuuurdrpn2id5hce`. Print each depth's blocks and bytes per group, the `run_records` count and bytes, and how many items lineage adds under the task rule. These numbers go in the report.
- Tests: fixture store with two runs, a Selection, nested Selection, Claims of each category logged in two members. Assert each depth's block sets by hand, the claim set, the skipped counts, the lineage fallback, and `missing_at_source`.

### T10 A first store-id on a member the cache holds nothing of resets nothing
- Found by T8: a cache that scanned a member while it had no `store-id` (an empty new destination) records `block_scan:<m>`, so `Index.reconcileStoreIds` no longer counts it as `holdsNothing`. The first real copy into that member creates its `store-id`, and every cache that scanned it then resets: the explore server's own, and any composition sharing `cas.index.path`. A reset in the middle of another catch-up can also leave a watermark covering deleted rows.
- Rule (DESIGN.md §20): a member with no recorded id and no watermark holds nothing when the cache attributes no row to it, whatever its scan flag says. The id is then recorded with no reset. Which rows count as attributed (`run.member`, `log_entry.member`, Selections and Claims a scan found) is decided from the code and stated in the test names.
- Tests, test-first, in the style of `IndexStoreIdTest`:
  - scan an empty member with no id, give it an id, and reconcile: no reset, and the id is recorded;
  - scan a member with no id that holds a run, give it an id with no watermark in its log, and reconcile: still resets (unchanged);
  - end to end through `CopyService`: an explore-style cache over `[lab, org]` with org empty, then a real copy into org, gives no "rebuilding the cache index" notice, and lab's rows are intact.
- Files: `core/Index.groovy`, tests. Nothing else.

### F1 rule
A Store Log entry a pre-P3 build skipped sits behind that build's watermark, and a pre-P3 snapshot carries no `transfer` rows. So a member whose transfer entries may have been skipped is read once in full for `transfer` entries:
- The trigger is either of two events: the cache gains the transfer tables on open (an existing v4 cache), or it is seeded from a snapshot without them.
- Mark each member `transfer_scan:<m>` pending. Its next catch-up lists the whole Store Log, ingests every `transfer` entry not yet indexed, and clears the mark.
- The test reproduces REV6: copy lab to org, then an org entry an hour later (watermark more than 10 minutes past the transfer), then a 270f03a-shaped snapshot without the transfer tables, then a P3 snapshot. Expect the Transfer rows, and org's figures at 11 B / 2 blocks, not 26 B / 4.

### F2 rulings, one per probe row (scrub and audit both, through the real RunManifest -> Records path)
Redacted and reported:
- a `--<flag>` whose name has a secret word, with the value after `=` or in the next token (`--api-key=abc`, `--password hunter2`), in params strings and config text (`process.ext.args`);
- the AWS secret-key shape: 40 characters of `[A-Za-z0-9/+=]` with upper case, lower case and a digit or `/`/`+`, standing alone. Hex digests (git SHAs, md5, sha1) stay;
- `Bearer <token>`; JWTs (`eyJ…` in three dot-separated segments); Slack `xox[abpr]-`; GitLab `glpat-`; Hugging Face `hf_`; and an Azure SAS `sig=` value in a query string;
- a secret-named key inside a JSON-ish string (`{"token": "abc123"}`);
- `auth` as a secret key segment (`env.API_AUTH`), matched as a segment so `author` stays;
- Windows paths (`C:\…`, `\\host\share`), `~/…` and `~user/…` paths, in values and in map keys. An absolute or `~` path used as a map key is redacted with a numbered suffix when two keys collide, so no entry is lost.

Kept (false-positive tests): an ordinary sample name; a relative path; `-1/3`; an email that is not the OS user's (`someone@example.org`); an IP before a path (the path is redacted, the IP kept); `--account=projX`; a git SHA; `cas://` and `lid://` links.

Afterwards, run the opt-in roblab audit on a scratch copy and report its count.

### F3 rule
Records under `nf/` that CasLinStore writes (WorkflowRun, TaskRun, FileOutput, ...) go through a field scrub before `DefaultLinStore` saves them:
- `homeDir`, the launch directory, the work directory and other absolute paths become `[redacted-location]`, using the same `Leaks` classifier;
- the fields Nextflow needs to resolve lineage (keys, `lid://` and `cas://` references, checksums) are kept.

Check `nextflow lineage list`, `view` and `find` against a gate sandbox with a scratch `NXF_HOME`, `NXF_PLUGINS_DIR` and `NXF_VER=26.04.6`, never `~/.nextflow`. If any of them breaks, there is no scrub; the report gives the evidence.

### F4 rule
A copy failure's message is `<ExceptionClass>: <message>`, with each member root (a local directory, or an S3 `s3://bucket/prefix`) replaced by its alias and any other absolute local path redacted. This applies to `failures[].error`, the snapshot outcome `"failed: <message>"`, and `/api/copy`'s 500 `copy_failed` body. A plan with nothing to transfer and no entry to add registers no Live Writer, so on S3 there is no PUT and no DELETE.
